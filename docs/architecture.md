# Decision-safe recovery architecture

One process-wide owner-aware inhibitor controls system sleep. Manual inhibition owns `manual`; resume owns a lease keyed by the hash of the Pi session ID and session file path. Releasing one lease cannot release another. Unexpected helper loss clears the affected owner snapshot and notifies the extension once; intentional final release does not emit a loss. The extension disables resume, cancels waits, persists the off state, and reports the failure. Scheduling and dispatch independently require an active session lease, so a stale enabled flag cannot resume unprotected. On Linux the owned inhibitor group runs a Pi-PID watchdog; macOS uses caffeinate's parent wait; Windows uses a hidden PowerShell watchdog and signals the owned positive PID on cleanup.

Persisted ON and OFF records apply only to the Pi session that wrote them. A fork does not inherit its parent's opt-in or acquire its lease, even when it copies the session ID. Moving a session to a different file or upgrading from ownerless or ID-only consent requires a new `/jb:keepgoing on`. Without a session file and ID, monitoring and timed waits are unavailable; manual sleep inhibition remains independent. A valid legacy submission timestamp attributed to the session ID still appears while Resume is OFF and enforces the five-minute repeat guard after a new opt-in. It never grants consent.

## Recovery path

On explicit activation, the latest message on the active branch may supply a retroactive eligible error. It enters the same guarded recovery path as a newly settled error; prior messages are not searched past a newer user or assistant message, and an already scheduled failure is not scheduled twice. Neither activation nor status sends a model turn. The shared activation/status report distinguishes waiting, monitoring without a timer, and off. Activation without an error is normal monitoring. Newly settled supported errors automatically emit the shared report with the deadline/countdown or scheduling failure; `/jb:keepgoing status` inspects the same state without side effects. Print/JSON slash activation cannot retain a timer after command return, so retroactive scheduling is unavailable there; settled-handler recovery remains blocking. Competing asynchronous reset lookups re-check the pending state before enqueue. No usable reset means no automatic schedule; no fallback deadline is guessed. The user-facing report shows actual sleep protection, observed reasons, one runtime-local deadline with seconds and timezone, a rounded countdown, and the requirement that Pi stay open. It is read-only; it neither queries providers nor repairs state.

1. `agent_end` records only an assistant `stopReason: error` from `openai-codex`, `anthropic`, or `claude-bridge` positively matching subscription-window exhaustion. Bridge accepts a `five_hour` wrapper with explicit session/five-hour/extra-usage exhaustion, or an explicit raw five-hour exhaustion; generic 429, monthly/weekly, auth, and billing errors are excluded.
2. `agent_settled` discards an aborted turn's recovery candidate without disabling monitoring or cancelling a separate timed wait. It also cancels pending provider timers and aborts provider lookups even when the run has no eligible final error. The failed message entry ID, not its text, is retained across tree navigation. Restore reads abort markers from all entries in the session file, not just the active branch, so navigating behind the marker or reloading cannot replay the failure. Only an un-aborted settlement proceeds to the idle, prompt and decision guards. Codex/Anthropic read an absolute reset from error text first; otherwise their provider-specific usage adapters query the Pi-managed OAuth token. Claude Bridge instead reads only an explicit zoned local reset minute from its assistant error. It never requests a token or uses either private endpoint. The zone belongs to the error, not to a configured city. Manual waits are elapsed durations; only the report converts a deadline to the Pi runtime’s local clock. [City examples](commands.md#timezones-and-waits).
3. An absolute deadline is set only for a usable reset, with a 90-second provider-reset buffer. Bridge parses `resets h[:mm]am/pm (IANA zone)` with optional minutes (`resets 4pm` means 4:00pm) and searches zoned wall-clock minutes after the error's timestamp (the current time when the message has no usable timestamp), waiting for the later occurrence when a DST rollback repeats a local minute, then fails closed if the reset is missing, invalid, or outside the six-hour bound from the error. A buffered reset that already passed no more than six hours ago (after `/reload` or a late `on`) schedules the continuation 5 seconds from now; an older one reports that the reset passed more than six hours ago. Only Claude Bridge takes this path; other providers' resets must be in the future. A job cannot wait more than six hours or immediately repeat within five minutes. After dispatch, Resume stays enabled for the next eligible exhaustion without a continuation-count ceiling; healthy usage creates no timer.
4. Immediately before firing, the extension checks enabled state, identical session, no blocking prompt/decision, idle Pi, and no queued user messages. One `sendUserMessage` continuation enters Pi's normal user-prompt pipeline with template expansion disabled; the failed assistant error is removed from the request context only while that resume is in flight.

While enabled, an unrecognized limit-like error from an allowlisted provider produces one console warning per error object: provider and fixed reason code only. `KEEPGOING_DEBUG=1` adds fixed family, window and reset-marker labels derived from the first 512 UTF-16 code units; no matched text or values are copied. The complete warning is capped at 160 ASCII characters. This projection is for display only: classification still sees the full error. Neither mode queries the provider, learns a retry rule or creates a timer. UI reports point to the summary; known warnings and permanent/unrelated errors are excluded.

## Timed continuation

`/jb:keepgoing wait 1h` or `wait 24m` schedules a single user message `Continue` without changing monitoring consent. From OFF, the timer alone owns the session lease and releases it on dispatch or cancellation. If the user explicitly enables monitoring before or during the wait, monitoring retains the lease. Rejected waits grant no consent or new lease; a rejected replacement preserves the pending timer. The independent manual lease is unchanged. These command timers require Pi to stay open; they cannot hold a single-shot runtime open after command return.

## Human control

`ui_prompt_start` and decision-tool execution cancel a pending job; `ui_prompt_end` only lowers the prompt guard and **never** schedules one. User input, session replacement, disablement, and shutdown invalidate pending timers. Cancellation aborts all outstanding reset lookups, even if no timer exists yet. A credential that arrives afterward is not sent; an in-flight usage request receives the abort signal. A generation check also discards late results without disturbing a newer timer. A pending deadline is intentionally not persisted across reload: enabled state, legacy counters, the repeat-guard timestamp, and validated same-session submission history may survive on the active session branch. Runtime diagnostics are not persisted. TUI waits use a scoped terminal-input listener to consume a lone Escape and unsubscribe on cancellation or completion; Pi reserves Escape and ignores extension shortcuts on that key. JSON and print await the pending deadline in the settled handler, so their single-shot runtimes cannot dispose the job early; TUI and RPC remain detached.

Pi does not expose byte-for-byte replay of the original provider request. The user-pipeline continuation preserves the session and conversational context, but the next provider payload is newly constructed; it is not a transparent HTTP retry. A submission timestamp records a call returning without a synchronous error, not guaranteed acceptance or model execution. Recovery observes eligible top-level assistant errors; it does not detect error-only subagent failures or relaunch subagents. Private usage endpoints may change without notice. See [developer details](implementation.md).
